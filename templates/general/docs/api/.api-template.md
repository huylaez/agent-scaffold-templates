# Documentation generation rules

This template defines structure only. Do not infer behavior from placeholders, examples, neighboring documents, naming conventions, or common framework behavior.

Verify all relevant implementation sources, including:

- route, handler, resolver, consumer, or command definitions;
- request and response schemas;
- validators and serialization behavior;
- authentication and authorization checks;
- service behavior relevant to the contract;
- exception handlers and error mappings;
- persistence or messaging behavior that affects visible outcomes.

Implementation code is the source of truth for implemented API-group documentation. `../api-contract.md` is the source of truth for the intended cross-system contract. If they disagree, resolve the conflict; do not silently choose one.

Never invent request or response fields, types, enum values, defaults, nullable behavior, constraints, statuses, error codes, authorization, side effects, ordering, pagination, or asynchronous behavior. If required information cannot be verified, write `Unknown from implementation`; otherwise omit the optional section.

Generate structurally minimal examples only from verified schemas. Explicitly distinguish required, optional, nullable, omitted, and defaulted fields.

When updating an existing interface, edit the existing section and remove behavior that is no longer supported. Do not add empty optional sections merely to match the template.
